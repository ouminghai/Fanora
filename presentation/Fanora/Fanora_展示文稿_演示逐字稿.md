# Fanora 展示文稿演示逐字稿

## 第 1 页 · 封面

大家好，我们是 Fanora。我们的项目想解决一个很简单、但在粉丝社区里长期存在的问题：很多热爱其实很真实，也很持续，但它往往只停留在一次签到、一条动态、一张截图，最后散落在不同平台里。Fanora 希望把这些参与和故事连接起来，让热爱成为可以被识别的身份，让故事成为可以被共创、收藏和长期保存的作品。

这次我们的 MVP 聚焦在 AI Agent 和 Web3 的结合：用 AI 理解粉丝故事，用 Web3 承载身份、贡献和最终作品的归属。我们的组员是软软的冬天、刘灿、xadrainMH、Jiayee Wu 和 teresa wu。

## 第 2 页 · 项目介绍

Fanora 连接的是三个阶段：参与、故事和作品。粉丝每天做的签到、互动、任务和陪伴，过去通常只是平台里的一个行为记录。但在 Fanora 里，这些行为会进入一个更长的链路。

第一步是参与，第二步是把参与背后的经历、情绪和场景沉淀成故事，第三步是把故事转化成专属、可迭代、可验证的数字纪念。也就是说，我们不是单纯做一个 NFT 生成器，而是想把粉丝的贡献变成一段可以继续生长的记忆。

## 第 3 页 · 问题

我们看到的问题是：粉丝一直在付出，但价值经常在平台切换中消失。比如每日签到、一条长帖、一次演出照片、一次粉丝任务、一次收藏记录，或者一次社区互动，它们本身都有意义，但彼此之间没有被真正连接起来。

结果就是贡献分散、成长断裂、故事失忆。粉丝不是没有贡献，而是这些贡献没有被理解、记录和长期保存。Fanora 想做的，就是把这些零散的行为重新组织成身份、故事和资产。

## 第 4 页 · 产品闭环

Fanora 的核心是一条闭环。用户从社区贡献开始，获得 FAN 和会员成长；当用户想把某段经历做成纪念品时，可以进入 AI Agent 共创流程；作品成熟后进入 Memory Forge；成功后通过 IPFS 和 Monad 保存并上链，最后进入 Gallery 被展示和收藏。

这里有六个关键节点，背后对应三层价值：体验层、创作层和资产层。我们希望保留 Web2 的简单体验，让用户不用理解复杂链上操作；同时让 AI 提供个性化创作能力，再由 Web3 提供长期验证和数字所有权。

## 第 5 页 · 身份与成长

在 Fanora 里，身份不是买来的，而是一次次参与积累出来的。用户通过签到、任务和互动获得 FAN；系统同时记录当前余额和终身累计贡献。这样一来，用户消费 FAN 不会导致身份倒退，因为等级依据的是长期贡献，而不是短期余额。

当用户成为正式会员后，还可以获得链上身份。这个身份是不可转让的 SBT，代表的是用户在社区里的真实参与关系。我们想强调的是：粉丝身份应该来自持续贡献，而不是一次性购买。

## 第 6 页 · AI 共创

Fanora 的 AI 不只是画一张图。我们更看重的是：AI 能不能听懂一段故事。用户不是输入一句随机 Prompt 就结束，而是通过多轮对话，把经历、情绪、场景和象征元素逐步讲清楚。

Agent 会持续维护 History 和 State，让创作过程不会丢失方向。它会结合模板、参考图和用户故事来生成草稿，只有在条件成熟时才调用图片生成工具。这样生成出来的作品，才更像是从粉丝经历里长出来的纪念品，而不是一张随机图片。

## 第 7 页 · Agent 工作流

这一页展示的是 LangGraph 的工作流。真正的共创不是一次 Prompt，而是一场持续对话。流程从加载视觉模板开始，然后理解用户故事，生成结构化草稿，再判断是否需要生图。如果需要，才调用受控的图片 Tool，最后保存 State 和 Trace。

我们设计了三个触发生图的条件：第一，用户明确要求生成图片；第二，如果第二轮仍然没有预览，就做首图兜底；第三，当模板、风格、参考图或核心 Prompt 已经成熟，才进行有效变化的生成。这样可以避免无意义的重复生图，也能在失败时保留对话、草稿和参考素材。

## 第 8 页 · Memory Forge

作品准备好之后，发行也应该是一场高光时刻。Memory Forge 会对作品做五维分析，包括原创性、视觉质量、粉丝情感、稀缺性和社区潜力。系统会基于这些维度给出发行建议，比如供应数量、FAN 价格，以及 Stable、Focused 或 Legendary 三种模式。

这里的边界很重要：AI 负责理解和建议，但确定性规则负责概率、结算和结果。换句话说，AI 可以帮助用户做更好的创作和策略选择，但资产相关的关键步骤必须可计算、可审计、可恢复。

## 第 9 页 · 失败可恢复

Forge 不一定每次成功，但失败不应该让故事归零。如果 Forge 成功，作品会进入正式发行链路：IPFS、ERC-1155，然后进入 Gallery。如果失败，作品、故事、预览、分析、策略和审计记录都会保留下来，用户还会获得 Memory Fragment。

这些 Fragment 未来可以兑换不同模式的 credit，比如 5 个兑换 Stable credit，10 个兑换 Focused credit。我们希望把失败从资产损失改造成成长反馈，同时保留游戏化的参与感。

## 第 10 页 · 发布链路

从预览到永久资产，中间必须经过严格校验。只有被确认的记忆，才进入永久保存和链上归属。流程先校验本人和成功的 Forge Session，然后规范化作品图片，再通过 Pinata 固定图片和 metadata，接着创建 ERC-1155 Token Type，最后 Mint 首枚并进入 Gallery。

这里我们区分了不同系统的职责：BeeImg 负责社区图片、模板、参考图和 AI 预览；IPFS 负责最终 NFT 图片和 metadata；Monad 负责 NFT、Badge、持有和交易证明。创作预览可以变化，但正式资产必须校验、固定、可追踪。

## 第 11 页 · 三分钟 Demo

现场 Demo 我们会用三分钟跑通一个端到端流程。首先是身份：钱包登录和正式会员卡。然后是贡献：签到、任务和 FAN 成长。接着进入最核心的共创环节：讲述故事、选择模板、多轮对话并生成预览。

之后我们会展示五维分析和发行建议，再进入 Forge，演示模式选择以及成功或失败的结果。最后展示链上结果，包括 IPFS、Monad 和 Gallery。如果现场 Forge 失败，我们不会把它当成事故，而是顺势展示 Fragment 和可恢复机制，再切换到预置成功作品。

## 第 12 页 · AI 与确定性边界

Fanora 的设计原则是：让 AI 保持想象力，让资产规则保持确定性。AI Agent 可以理解故事和情绪，可以推荐模板、优化 Prompt，可以请求生成图片，也可以给出评分和发行建议。

但 AI Agent 不可以直接扣除 FAN，不可以决定或伪造 Forge 随机结果，不可以直接写入 IPFS，也不可以持有私钥或发送合约交易。确定性服务负责鉴权、余额、事务、幂等、概率、随机判定、IPFS 固定和 Monad 交易。这样才能同时保留 AI 的创造力和资产系统的可信度。

## 第 13 页 · 系统架构

系统架构这里我们用一个自下而上的分层图来说明。最底层是 Data & Model Store，负责 PostgreSQL、Pinata、BeeImg、Monad，以及 LLM 和图像生成模型这些基础能力。往上是核心业务逻辑和确定性领域服务，承接会员、社区、FAN、Forge、NFT 发布和购买这些必须稳定结算的业务。

中间层是 Intelligent Orchestration，也就是基于 LangGraph 的 Agent 编排，负责 NFT Studio Agent、用户画像和审核 Agent。再往上是 API、鉴权和连接枢纽，基于 FastAPI 和 Pydantic 提供可靠接口、角色控制和安全连接。最上面是 Presentation Layer，也就是用户看到的 Web 应用层。关键保障包括事务与幂等、模型失败保留状态、Pinata 失败不 Mint、链上失败恢复 FAN，以及私钥只在服务端。

## 第 14 页 · 链上与站内分工

我们不会把所有东西都放到链上。高频业务留在站内，长期价值交给 Monad。站内事实包括用户、社区、任务、签到、FAN 流水，Agent 对话状态与 Checkpoint，以及模板、参考图、预览和 Forge Session。

链上事实则包括正式会员身份、NFT、Badge、收藏品，以及最终图片和 metadata。这样的分工可以保留 Web2 的交互效率，同时让关键身份和作品拥有长期可验证的归属。

## 第 15 页 · 已实现

目前我们的 MVP 已经打通从热爱到链上收藏的最后一公里。完整路径包括身份、贡献、AI 共创、Forge、IPFS + Monad，以及 Gallery。

已经实现的部分包括：钱包登录、正式会员、链上身份和动态会员卡；社区、任务、签到、FAN、等级、排行榜和粉丝画像；数据库模板、多轮 Agent、Tool、参考图和多模态预览；五维分析、三种 Forge 模式、Fragment 和幂等结算；BeeImg、Pinata IPFS、Monad ERC-1155 发布链路；以及 Gallery、互动、FAN 购买和个人 Collection。

本次我们刻意不做二级交易市场、跨链资产、DAO 治理、法币支付、法律意义的版权确权，以及完整多社区运营后台。我们希望先把核心闭环做完整。

## 第 16 页 · 结尾

最后，我们想回到 Fanora 最核心的价值：收藏的不只是一张图，更是“我为何热爱”。贡献不再消失，而是沉淀为身份；故事不再停留在回忆里，而是成为专属作品；收藏也不再只有交易价值，而是记录真实关系与成长。

Fanora 的路径是：连接钱包，参与社区，与 Agent 共创，进入 Forge，最后收藏上链。我们希望让热爱被记录，让身份被认可，让记忆拥有归属。

## 第 18 页 · 附录 A：Forge 规则

这一页是 Forge 规则的补充说明。Forge 不是简单按一下随机数，而是策略对概率的可审计影响。成功概率由 base、QualityFactor、SupplyFit、PriceFit、LevelBonus 和 ModeModifier 共同决定，最终会限制在 20% 到 95% 之间。

RareScore 的五维权重分别是原创性 25%、视觉质量 20%、粉丝情感 25%、稀缺性 20%、社区潜力 10%。三种模式分别对应不同风险和成本：Stable 更稳健，Focused 平衡成本与修正，Legendary 更强调高风险和稀缺叙事。每次尝试都会记录概率、roll、规则版本和结算结果。

## 第 19 页 · 附录 B：LangGraph

这一页补充 NFT Studio Agent 的内部结构。多轮一致性来自可追踪节点，而不是把所有希望塞进一个 Prompt。整个流程包括模板加载、模板 Tool、故事访谈、作品草稿、生图规划、图片 Tool 和结果应用。

State 里保存六类信息：Conversation、Visual Context、Story State、Artifact Draft、Generation Memory 和 Tool State。LangGraph 会保存 History 和 State，Tool 调用、降级原因和结果应用都可以留下 Trace。这是我们保证共创过程可恢复、可追踪的关键。

## 第 20 页 · 附录 C：合约与部署

链上只承载关键身份、收藏品和持有关系。我们使用 Monad Testnet，Chain ID 是 10143。合约包括 FanoraMembershipGateway、FanoraMembershipIdentity 和 FanoraCollectibles。

其中 Gateway 负责会员激活与支付防重放，MembershipIdentity 负责 ERC-721 不可转让会员身份，Collectibles 负责 ERC-1155 NFT、Badge 和收藏品。部署地址来源于 shared/contracts/monadTestnet.deployment.json。私钥和服务 Token 只存在服务端，链上交易由确定性服务发起和确认。

## 第 21 页 · 附录 D：安全与恢复

最后是安全和恢复机制。关键资产操作必须幂等、可审计、可恢复。比如钱包登录使用一次性 Challenge 和服务端会话，避免重复创建身份。任务、FAN 和 Fragment 使用事务与幂等键，保证奖励不重复、余额一致。

Forge 会保存概率、roll、规则版本和结算结果，所以即使失败也能保留作品并获得恢复反馈。IPFS 和 Monad 的发布链路要求 Pinata 成功后才 Mint，链上失败则回滚状态，不标记假成功，购买失败也会恢复 FAN。对于 LLM、Image Model 或 Redis 这类外部依赖，我们也定义了降级边界和重试入口。AI 可以失败，外部服务可以超时，但资产事实不能模糊。
