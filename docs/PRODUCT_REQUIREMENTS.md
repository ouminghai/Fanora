# Fanora Protocol 产品与开发需求文档

> 项目名称：Fanora Protocol（凡诺拉协议 / 粉环协议）\
> 项目定位：AI Agent 驱动的 Web3 链上粉丝身份与互动平台\
> 文档版本：v1.0\
> 文档日期：2026-07-16\
> 需求状态：开发规划\
> 核心网络：Monad Testnet（MVP）

## 1. 文档使用方法

- `[ ]` 表示尚未完成。
- `[x]` 表示已经完成并通过当前阶段验证。
- 每条需求都包含唯一编号，提交代码、测试记录和答辩材料应引用对应编号。
- `MVP` 表示首个可演示版本必须完成，`P1` 表示增强版本，`P2` 表示远期能力。
- 需求只有在功能实现、验收标准满足、相关测试通过后才能核销。

## 2. 产品定位与目标

- [ ] `OBJ-001 [MVP]` 建立“登录无感、钱包必备”的身份体系；验收：非 Web3 用户通过邮箱、社交账号或 Passkey 登录时自动获得嵌入式钱包，Web3 用户可连接外部钱包，所有已激活账户都必须绑定至少一个唯一钱包地址。
- [ ] `OBJ-002 [MVP]` 建立创作者与粉丝之间可验证的互动任务体系；验收：创作者可发布任务，粉丝可参与，后端可验证并记录结果。
- [ ] `OBJ-003 [MVP]` 建立积分、等级和 Badge 联动的成长体系；验收：完成任务后产生积分流水，积分达到阈值后可获得或升级链上 Badge。
- [ ] `OBJ-004 [MVP]` 建立 AI 粉丝身份画像 Agent；验收：Agent 能根据结构化行为数据输出身份评分、粉丝类型和解释。
- [ ] `OBJ-005 [MVP]` 实现 Proof of Fandom 粉丝证明；验收：用户可通过不可转让的链上 Badge 证明其粉丝等级和长期贡献。
- [ ] `OBJ-006 [P1]` 为创作者提供轻量任务管理、粉丝查询和基础数据统计；验收：创作者可管理自己的任务并查看真实统计数据，不提供 Agent 运营决策后台。
- [ ] `OBJ-007 [P2]` 将 Fanora 身份凭证开放给第三方应用组合使用；验收：外部应用可通过合约或公开接口查询用户 Badge 和公开身份摘要。

## 3. 核心概念

| 概念                | 定义                                       |
| ----------------- | ---------------------------------------- |
| Fan Identity      | 以钱包地址为主体，结合任务、积分、行为和 Badge 形成的粉丝身份。      |
| Proof of Fandom   | 将长期参与、真实互动、早期支持和贡献记录组合成可验证身份凭证的机制。       |
| Fan Profile       | Agent 生成的粉丝画像，包括活跃度、忠诚度、影响力、贡献度、风险和粉丝类型。 |
| Dynamic Badge     | 可随粉丝成长发生等级和 metadata 变化的链上身份徽章。          |
| SBT               | 不允许普通用户转让的灵魂绑定身份凭证。                      |
| Creator Community | 由创作者建立并运营的粉丝社区，是任务、积分和 Badge 的归属范围。      |
| Embedded Wallet   | 用户快捷登录后由专业钱包提供商自动创建的钱包，不要求用户安装插件。     |
| Primary Wallet    | Fanora 用于接收 Badge 和标识链上身份的主钱包。              |
| Identity Abstraction | 业务模块只识别统一用户和主钱包，不感知具体登录方式。             |

### 3.1 LangGraph 使用范围

- [ ] `SCOPE-AGENT-001 [MVP]` LangGraph 只用于粉丝画像、身份评分解释和粉丝任务推荐；验收：后台管理接口不调用 Agent 进行权限或运营决策。
- [ ] `SCOPE-AGENT-002 [P1]` LangGraph 可在确定性积分条件触发后生成 Badge 名称、描述和 metadata 草案；验收：草案必须经过创作者确认才能进入发行流程。
- [ ] `SCOPE-AGENT-003 [MVP]` LangGraph 不参与角色管理、任务发布审批、积分修改、审计处理和链上交易重试。
- [ ] `SCOPE-AGENT-004 [MVP]` 创作者后台保持轻量；验收：MVP 只提供任务管理、基础统计、粉丝列表和 Badge 草案确认。

## 4. 用户角色与权限

- [ ] `ROLE-001 [MVP]` 支持普通粉丝 `fan` 角色；验收：可登录、参与任务、查看积分、画像和 Badge，不可执行创作者或管理员操作。
- [ ] `ROLE-002 [MVP]` 支持创作者 `creator` 角色；验收：可创建和管理自己的社区、任务、徽章配置并查看本社区数据。
- [ ] `ROLE-003 [MVP]` 支持运营账户 `operator` 角色；验收：只能在后端完成验证后执行受控的 Badge 铸造或升级操作。
- [ ] `ROLE-004 [MVP]` 支持管理员 `admin` 角色；验收：仅提供角色、失败任务、链上交易和审计记录等必要操作，不建设复杂运营后台。
- [ ] `ROLE-005 [MVP]` 实现资源归属校验；验收：创作者不能查看或修改不属于自己的社区和任务。
- [ ] `ROLE-006 [P1]` 支持同一钱包同时拥有粉丝和创作者身份；验收：用户能切换工作区，权限不会互相泄漏。

## 5. MVP 核心业务闭环

- [ ] `FLOW-001 [MVP]` 用户选择快捷登录，或选择连接已有 Web3 钱包。
- [ ] `FLOW-002 [MVP]` 快捷登录用户自动创建或恢复嵌入式钱包；外部钱包用户通过 nonce 完成签名验证。
- [ ] `FLOW-003 [MVP]` 后端验证登录凭证，确保账户绑定唯一主钱包后创建统一会话。
- [ ] `FLOW-004 [MVP]` 用户进入创作者社区并领取一个签到或链上验证任务。
- [ ] `FLOW-005 [MVP]` 用户提交任务结果，后端通过规则或链上数据进行验证。
- [ ] `FLOW-006 [MVP]` 验证通过后写入任务完成记录和不可重复的积分流水。
- [ ] `FLOW-007 [MVP]` Agent 根据最新行为数据更新身份评分和粉丝类型。
- [ ] `FLOW-008 [MVP]` 系统根据确定性规则判断 Badge 铸造或升级资格。
- [ ] `FLOW-009 [MVP]` 后端运营账户调用 Monad 合约完成 Badge 铸造或升级。
- [ ] `FLOW-010 [MVP]` 前端 Dashboard 展示用户积分、等级、粉丝画像、任务状态和链上 Badge。

## 6. 功能需求

### 6.1 无感登录与强制钱包身份

- [ ] `AUTH-001 [MVP]` 提供面向普通用户的快捷登录入口；验收：至少支持邮箱验证码、社交账号或 Passkey 中的一种方式，默认不要求安装钱包插件。
- [ ] `AUTH-002 [MVP]` 快捷登录成功后自动创建或恢复嵌入式钱包；验收：用户首次进入核心功能前已经拥有 Monad 兼容地址。
- [ ] `AUTH-003 [MVP]` 强制执行钱包绑定不变量；验收：没有主钱包地址的账户不能激活，也不能领取任务、获得积分或接收 Badge。
- [ ] `AUTH-004 [MVP]` 嵌入式钱包创建过程对非 Web3 用户保持无感；验收：默认流程不展示助记词、RPC、Gas、切链或复杂签名术语。
- [ ] `AUTH-005 [MVP]` Fanora 后端不得生成、保存或记录用户嵌入式钱包私钥；验收：密钥托管、MPC 或 Passkey 签名由专业钱包提供商完成。
- [ ] `AUTH-006 [MVP]` 后端验证嵌入式钱包提供商签发的身份令牌；验收：校验签名、签发者、受众、过期时间、用户标识和钱包地址。
- [ ] `AUTH-007 [MVP]` 支持 MetaMask 外部钱包连接；验收：Web3 用户可连接、断开并查看缩略地址。
- [ ] `AUTH-008 [MVP]` 支持 WalletConnect 兼容钱包；验收：配置有效 Project ID 后可通过二维码或移动钱包连接。
- [ ] `AUTH-009 [MVP]` 外部钱包登录时检测当前链；验收：非 Monad Testnet 时显示切链按钮和明确提示。
- [ ] `AUTH-010 [MVP]` 外部钱包支持一键切换至 Monad Testnet；验收：钱包中没有该网络时可以自动添加网络配置。
- [ ] `AUTH-011 [MVP]` 后端为外部钱包生成一次性登录 nonce；验收：nonce 随机、具备过期时间、使用后立即失效。
- [ ] `AUTH-012 [MVP]` 外部钱包签名消息包含域名、钱包地址、nonce、链 ID、签发时间和过期时间。
- [ ] `AUTH-013 [MVP]` 后端验证外部钱包签名；验收：签名地址、消息内容、nonce 和有效期全部正确时才允许登录。
- [ ] `AUTH-014 [MVP]` 两种登录方式统一创建 Fanora 会话；验收：业务模块只读取统一用户 ID 与主钱包，不判断登录提供商。
- [ ] `AUTH-015 [MVP]` 同一钱包地址只能绑定一个 Fanora 用户；验收：并发注册、大小写差异和重复关联不能创建多份身份。
- [ ] `AUTH-016 [P1]` 支持登录后关联外部钱包；验收：关联前必须重新认证，且目标钱包需要签名证明所有权。
- [ ] `AUTH-017 [P1]` 支持切换主钱包；验收：切换需要高风险操作确认，并明确提示已有 SBT Badge 不能自动迁移。
- [ ] `AUTH-018 [P1]` 支持嵌入式钱包恢复或导出策略；验收：恢复能力由钱包提供商实现，Fanora 不接触明文私钥。
- [ ] `AUTH-019 [P1]` 支持 Gas 赞助或账户抽象；验收：普通用户领取 Badge 时无需理解或准备 MON，费用与限额受到服务端策略控制。
- [ ] `AUTH-020 [MVP]` 支持退出登录；验收：退出后服务端会话和提供商会话按策略失效。
- [ ] `AUTH-021 [MVP]` 对快捷登录、nonce、签名验证和钱包关联实施速率限制，并记录安全事件。

### 6.2 用户、创作者与社区

- [ ] `USER-001 [MVP]` 首次登录时创建统一用户；验收：用户记录与登录身份、钱包记录分离，主钱包地址按校验和格式存储并具备唯一约束。
- [ ] `USER-002 [MVP]` 用户可设置昵称和头像；验收：昵称长度、图片类型和大小受到限制。
- [ ] `USER-003 [MVP]` 用户主页展示地址、等级、积分、粉丝类型和 Badge；验收：公开信息和私有信息严格区分。
- [ ] `USER-004 [MVP]` 用户可查看自己的积分明细；验收：每条记录包含来源、数值、时间和关联任务。
- [ ] `USER-005 [P1]` 用户可设置公开资料范围；验收：隐藏的画像维度不能通过公开接口读取。
- [ ] `CREATOR-001 [MVP]` 管理员可授予创作者身份；验收：普通用户不能自行提升权限。
- [ ] `CREATOR-002 [MVP]` 创作者可创建社区；验收：必须填写名称、简介、Logo 和社区标识。
- [ ] `CREATOR-003 [MVP]` 创作者可编辑自己的社区资料；验收：更新后前端和接口数据一致。
- [ ] `CREATOR-004 [MVP]` 社区具备独立积分、任务、等级和 Badge 配置；验收：不同社区的数据不能混算。
- [ ] `CREATOR-005 [P1]` 支持一个社区配置多个管理员；验收：每个管理员具有可撤销的细粒度权限。
- [ ] `COMMUNITY-001 [MVP]` 用户可浏览公开社区列表；验收：支持基本分页和名称搜索。
- [ ] `COMMUNITY-002 [MVP]` 用户可加入或关注社区；验收：重复操作不会产生重复成员记录。

### 6.3 粉丝互动任务

- [ ] `TASK-001 [MVP]` 创作者可创建任务草稿；验收：任务包含标题、描述、类型、开始时间、结束时间、奖励积分、验证规则和参与限制。
- [ ] `TASK-002 [MVP]` 创作者可发布、暂停和结束任务；验收：状态转换符合草稿、已发布、已暂停、已结束的合法顺序。
- [ ] `TASK-003 [MVP]` 支持每日签到任务；验收：同一用户在同一自然日只能完成一次。
- [ ] `TASK-004 [MVP]` 支持链上资产持有验证任务；验收：后端通过 web3.py 查询指定合约和区块高度下的真实持有状态。
- [ ] `TASK-005 [MVP]` 支持链上交易验证任务；验收：交易链 ID、发送方、接收方、状态和确认数全部符合规则。
- [ ] `TASK-006 [MVP]` 支持平台内部互动任务；验收：任务行为必须由服务端记录，不能只相信前端提交结果。
- [ ] `TASK-007 [P1]` 支持人工审核任务；验收：用户可提交文本或图片凭证，创作者可批准或拒绝并填写原因。
- [ ] `TASK-008 [P1]` 支持 X 互动验证任务；验收：使用官方授权方式读取必要数据，并处理接口不可用和授权失效。
- [ ] `TASK-009 [P1]` 支持 Discord 成员或角色验证；验收：用户授权后可验证服务器成员和角色状态。
- [ ] `TASK-010 [P2]` 支持 Telegram 和 GitHub 等扩展验证适配器；验收：新增平台无需修改任务核心模块接口。
- [ ] `TASK-011 [MVP]` 粉丝可浏览可参与任务；验收：过期、未开始、不满足条件和已完成任务具有明确状态。
- [ ] `TASK-012 [MVP]` 粉丝可领取任务；验收：重复领取不会创建重复记录。
- [ ] `TASK-013 [MVP]` 粉丝可提交任务结果；验收：提交内容经过格式校验并记录提交时间。
- [ ] `TASK-014 [MVP]` 后端采用幂等任务验证；验收：重复请求不会重复完成任务或重复发放积分。
- [ ] `TASK-015 [MVP]` 任务结果支持待验证、已通过、已拒绝、已奖励状态；验收：每次状态变更写入审计记录。
- [ ] `TASK-016 [MVP]` 失败验证返回可理解原因；验收：错误信息不泄露内部密钥、规则绕过方式或其他用户数据。
- [ ] `TASK-017 [P1]` 支持任务前置条件；验收：可配置最低等级、指定 Badge、加入社区时间等条件。
- [ ] `TASK-018 [P1]` 支持任务总名额和单用户次数限制；验收：并发参与时不会超发名额或奖励。

### 6.4 积分、经验和等级

- [ ] `POINT-001 [MVP]` 建立不可直接修改的积分流水；验收：积分余额由流水汇总得到，每条流水具有唯一业务幂等键。
- [ ] `POINT-002 [MVP]` 任务验证通过后自动增加积分；验收：发放数值与任务发布时保存的奖励快照一致。
- [ ] `POINT-003 [MVP]` 支持管理员纠错积分；验收：只能通过新增正向或负向调整流水修正，不能删除历史记录。
- [ ] `POINT-004 [MVP]` 社区积分相互隔离；验收：同一用户在不同社区拥有独立积分余额。
- [ ] `LEVEL-001 [MVP]` 支持配置等级阈值；验收：至少提供 Emerging、Bronze、Silver、Gold、Core 五个阶段。
- [ ] `LEVEL-002 [MVP]` 积分变化后自动重新计算等级；验收：等级计算具有确定性且可重复执行。
- [ ] `LEVEL-003 [MVP]` 前端展示当前等级和下一等级进度；验收：进度与后端计算结果一致。
- [ ] `LEVEL-004 [P1]` 等级条件支持积分与 Agent 评分组合；验收：阈值规则版本可追踪，历史升级能还原判断依据。
- [ ] `RANK-001 [P1]` 提供社区积分排行榜；验收：支持周期、分页和当前用户排名查询。
- [ ] `RANK-002 [P1]` 提供活跃度和贡献度排行榜；验收：明确展示统计周期与更新时间。
- [ ] `BENEFIT-001 [P1]` 支持等级权益配置；验收：创作者可配置专属内容、活动资格或白名单说明。
- [ ] `BENEFIT-002 [P2]` 支持外部应用校验等级权益；验收：第三方可验证凭证但不能读取用户私有画像。

### 6.5 链上粉丝身份与 Badge

- [ ] `BADGE-001 [MVP]` 使用 ERC-1155 表达多个粉丝等级 Badge；验收：一个合约可查询不同 Badge ID 的余额。
- [ ] `BADGE-002 [MVP]` Badge 必须不可在普通用户之间转让；验收：转账交易回滚，铸造和销毁仍可执行。
- [ ] `BADGE-003 [MVP]` 只有具备 `MINTER_ROLE` 的账户可以铸造和升级；验收：未授权账户调用时交易回滚。
- [ ] `BADGE-004 [MVP]` 首次达到门槛时铸造 Bronze Badge；验收：同一社区、同一等级不会重复铸造。
- [ ] `BADGE-005 [MVP]` 身份升级时销毁旧 Badge 并铸造新 Badge；验收：升级完成后用户仅持有当前有效等级 Badge。
- [ ] `BADGE-006 [MVP]` 记录 Badge 铸造和升级交易；验收：数据库保存链 ID、合约地址、交易哈希、Badge ID 和确认状态。
- [ ] `BADGE-007 [MVP]` 前端展示链上 Badge 状态；验收：数据来源为合约读取，并提供区块浏览器链接。
- [ ] `BADGE-008 [MVP]` Badge metadata 包含名称、等级、图片、社区和凭证说明；验收：URI 可通过标准 ERC-1155 方式读取。
- [ ] `BADGE-009 [P1]` 支持动态更新 Badge metadata；验收：更新后可追踪 metadata 版本，不改变用户身份归属。
- [ ] `BADGE-010 [P1]` 支持多个创作者社区的 Badge 命名空间；验收：不同社区的 Badge ID 不发生冲突。
- [ ] `BADGE-011 [P1]` 展示 Proof of Fandom 可验证摘要；验收：摘要不包含私密原始社交数据。
- [ ] `BADGE-012 [P2]` 支持第三方协议读取公开 Badge；验收：提供稳定 ABI、合约地址和开发说明。

### 6.6 AI Agent 粉丝画像与 Badge 草案

## 11. 安全与隐私需求

- [ ] `SEC-001 [MVP]` 所有真实密钥仅保存在后端或部署环境的密钥系统中。
- [ ] `SEC-002 [MVP]` 前端环境变量中不得出现 OpenAI Key、运营私钥、管理员私钥或数据库密码。
- [ ] `SEC-003 [MVP]` 使用独立 Monad Testnet 测试钱包，不使用存有真实资产的主钱包。
- [ ] `SEC-004 [MVP]` 登录签名必须防止重放攻击；验收：nonce 一次性、限时并绑定域名和链 ID。

- [ ] `SEC-008 [MVP]` 日志对钱包以外的敏感身份信息、令牌和密钥进行脱敏。
- [ ] `SEC-009 [MVP]` Agent 输出不能直接触发敏感动作；验收：奖励和铸造必须经过确定性规则与权限检查。

## 16. MVP 完成定义

以下项目全部核销后，Fanora MVP 才视为完成：

- [ ] `DOD-001` 非 Web3 新用户可通过快捷登录无感获得 Monad 钱包并进入产品，Web3 用户可使用外部钱包签名登录，所有已激活账户均拥有唯一主钱包。
- [ ] `DOD-002` 创作者可以建立社区并发布至少一种可自动验证的任务。
- [ ] `DOD-003` 粉丝可以领取、提交并完成任务，且重复请求不会重复奖励。
- [ ] `DOD-004` 用户可以查看准确的积分流水、当前等级和升级进度。
- [ ] `DOD-005` LangGraph Agent 可以生成结构化粉丝画像，并在模型失败时降级到规则结果。
- [ ] `DOD-006` 达到资格的用户可以在 Monad Testnet 获得不可转让 Badge。
- [ ] `DOD-007` 用户可以在前端查看链上 Badge 和对应浏览器记录。
- [ ] `DOD-008` 创作者可以查看社区基础数据、任务完成情况和粉丝列表。
- [ ] `DOD-009` 关键权限、幂等、安全和合约测试全部通过。
- [ ] `DOD-010` 项目可以根据开发文档在新环境中启动和演示。

## 17. 暂不纳入 MVP

以下内容不属于第一版验收范围，避免项目过度扩张：

- 多链部署和跨链身份聚合。
- DAO 治理、协议代币和真实空投发放。
- 完整接入 X、Discord、Telegram、GitHub 等所有平台。
- 使用多个自治 Agent 互相调用的复杂架构。
- AI 运营报告、创作者聊天助手和复杂管理员工作台。
- 将完整粉丝画像、社交原始数据和频繁变化的积分全部写入链上。
- 未经安全评估直接部署主网或管理真实资产。
