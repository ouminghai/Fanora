# Fanora MVP 路线图

> 版本：v1.3\
> 更新日期：2026-07-20\
> 需求基线：[PRODUCT_REQUIREMENTS.md](./PRODUCT_REQUIREMENTS.md)\
> 架构基线：[ARCHITECTURE.md](./ARCHITECTURE.md)

## 1. 路线原则

- 先完成 PostgreSQL 中可验证、可审计的业务闭环，再增加链上凭证。
- ERC-721 会员身份与 ERC-1155 纪念资产分开实现、测试和部署。
- Pinata metadata 成功固定后才允许链上铸造。
- Agent 不成为积分、等级、审核或合约权限的前置依赖。
- 每个阶段必须有退出条件；页面展示或文档完成不能替代业务验收。

## 2. 当前基线

### 已完成

- Web3Auth 快捷登录、钱包签名挑战、统一用户与会话。
- 用户资料、主钱包数据模型、官方社区展示与加入。
- 1 MON 正式入会交易验证。
- 会员等级、Fan Token 规则和首页真实等级展示。
- FastAPI、LangGraph、PostgreSQL/Alembic 和本地开发基础。
- ERC-1155 SBT 技术原型及基础测试。

### 尚未形成闭环

- 外部钱包完整登录与主钱包管理。
- 任务、验证、积分流水和等级变化事件。
- Pinata 与 NFT metadata 版本。
- ERC-721 会员身份和 ERC-1155 纪念资产目标合约。
- 链上异步写入、事件对账和前端资产页面。

## 3. 阶段 1：任务、积分与等级事实源

目标：完成第一条不依赖 NFT 的真实业务闭环。

交付物：

1. 固定一条 Fanora 官方社区记录，不开发社区创建、列表、搜索和切换。
2. `tasks`、`task_claims`、`point_ledger` 数据模型和迁移，所有数据均为平台全局数据。
3. 至少一个每日签到或平台内部任务。
4. 领取、提交、服务端验证、幂等奖励和失败原因。
5. 单一全局积分流水、余额与等级计算。
6. 前端任务中心、积分明细和升级进度。

退出条件：

- 重复提交不重复发积分。
- 积分余额可由流水重算。
- 等级变化有规则版本和审计证据。
- 前端不再依赖任务与积分 mock 数据完成演示。

## 4. 阶段 2：Pinata 与 ERC-721 会员身份

目标：把正式会员和积分等级转化为唯一、不可转让的链上会员证。

交付物：

1. Pinata Adapter、图片上传、metadata JSON、CID 与版本表。
2. `FanoraMembershipIdentity` ERC-721 SBT。
3. 唯一钱包身份、有效 levelId、operationId 防重和暂停机制。
4. 正式会员首次身份铸造。
5. 积分升级时保持 tokenId 不变并更新 levelId 与 metadata。
6. 后端交易提交、确认、失败重试和事件对账。
7. 前端会员证与链上同步状态。

退出条件：

- 同一钱包不能重复铸造会员身份。
- 所有 ERC-721 转让入口和授权绕过测试失败即回滚。
- 同一 operationId 不会重复铸造或升级。
- Pinata 失败不会提交临时 URI 到链上。
- Monad Testnet 可查看真实 token、交易和 `ipfs://` metadata。

## 5. 阶段 3：ERC-1155 纪念资产与限定 Badge

目标：完成三类粉丝纪念资产的统一发行能力。

交付物：

1. `FanoraCollectibles` ERC-1155。
2. `CONCERT_CARD`、`CUSTOM_BADGE`、`TASK_LIMITED_BADGE` 三类 token。
3. 最大供应量、累计钱包限额、领取时间窗、转让策略和 metadata 冻结。
4. claimKey 链上与数据库双重防重。
5. 演唱会打卡或领取名单发放纪念卡。
6. 完成任务后领取限定 Badge。
7. 前端收藏页与领取状态。

退出条件：

- 超发、超钱包限额、过期领取和重复 claimKey 全部回滚。
- 不可转让 token 的单笔与批量转移都被阻止。
- 演唱会纪念卡每次发放都有可追踪任务或名单依据。
- 资产余额、发行量和数据库记录可与链上事件对账。

## 6. 阶段 4：用户自定义 NFT 申请

目标：让正式会员可以安全申请个人纪念徽章。

交付物：

1. 自定义 NFT 申请页面与状态机。
2. 受控临时审核存储、文件校验和内容检查。
3. 创作者/运营/管理员审核与审计日志。
4. 批准后上传 Pinata、创建 `CUSTOM_BADGE` token 类型并铸造给申请人。
5. 用户查看审核、Pinata 和铸造状态。

退出条件：

- 未批准内容不会进入公开 IPFS 或链上。
- 越权审批与任意铸造地址被服务端拒绝。
- 自定义徽章供应量和单钱包上限均为 1。
- 修改已批准内容必须重新审核并产生新 CID。

## 7. 阶段 5：Agent、创作者控制台与 Proof of Fandom

目标：将已完成的任务、积分和链上资产组合成可解释的粉丝身份体验。

交付物：

1. 真实任务和积分数据接入 LangGraph。
2. 粉丝画像版本、降级结果和 Dashboard。
3. 推荐任务与 ERC-1155 metadata 草案。
4. 创作者基础统计、粉丝筛选、资产分布和 NFT 申请审核队列。
5. MVP 端到端演示数据与答辩材料。

退出条件：

- Agent 失败时仍返回确定性规则结果。
- Agent 不能修改积分、等级、审核或链上交易。
- 创作者只能访问授权的官方社区内容管理接口，不能执行角色、积分纠错或系统配置操作。
- 快捷登录与外部钱包至少各完成一次人工端到端验收。

## 8. 阶段 6：部署与发布验收

1. 两个合约部署至 Monad Testnet。
2. ABI、地址、chainId 和事件起始区块同步到前后端。
3. Pinata 使用独立项目和最小权限 JWT。
4. 管理员、铸造、等级、类型、URI 和暂停角色分离。
5. 完成权限、上传安全、幂等、链重组和事件对账测试。
6. 按 `PRODUCT_REQUIREMENTS.md` 的 MVP 完成定义逐项核销。

## 9. 暂不纳入 MVP

- 多社区创建、社区列表搜索和社区切换。
- 按社区拆分积分、任务、等级、Badge 和排行榜。
- 多社区管理员与细粒度社区权限系统。
- 多链和跨链身份聚合。
- DAO、协议代币和真实空投。
- NFT 二级市场、拍卖和版税分账。
- 将完整积分、任务或粉丝画像写入链上。
- 一次接入全部 X、Discord、Telegram 等外部数据源。
- AI 自动审批、自动修改积分或直接控制合约。
- 未经安全评估的 Monad 主网部署。
