# Fanora 系统架构

## 1. 总体原则

Fanora 当前采用“模块化单体 + 独立合约工程”，不在项目早期拆微服务。这样既保留清晰的模块接口，也降低部署、调试和学习成本。

```text
浏览器 / 钱包
     │
     ├── 公开链上读取、用户签名 ────────> Monad 合约
     │
     └── 登录、任务、画像、创作者操作 ──> FastAPI
                                            │
                                            ├── LangGraph Agent
                                            ├── 数据库 / 社交平台适配器
                                            └── web3.py ─────────> Monad 合约
```

## 2. 关键接口位置

### 前端与后端

前端只依赖稳定的 HTTP/JSON 接口，不了解 Agent 节点、数据库表或链上写入细节。建议统一使用 `/api/v1` 前缀。

### 后端与 Agent

业务模块只调用“生成粉丝画像”这一个高层接口。LangGraph 的节点数量、模型选择和提示词留在 Agent 模块内部。

### 后端与区块链

任务和身份模块不直接散落调用 web3.py。所有查询、铸造和升级动作由区块链适配器集中实现，方便测试时换成内存假实现。

### 前端与合约

前端可以直接读取 Badge 余额等公开数据。铸造、升级等受权限控制的操作由后端验证后提交，不能把管理员私钥放进前端。

## 3. 第一阶段数据归属

- 链上：Badge 类型、持有状态、升级事件、关键凭证摘要。
- 数据库：用户资料、任务定义、任务进度、积分明细、Agent 分析结果。
- 对象存储/IPFS：徽章图片和 metadata。

不要把完整用户画像、社交平台原始数据或频繁变化的积分明细全部写到链上。

## 4. 第一阶段角色

- `fan`：连接钱包、参与任务、查看画像和徽章。
- `creator`：创建社区和任务、查看粉丝分层。
- `operator`：后端受控账户，负责验证后铸造或升级 Badge。
- `admin`：管理合约角色和系统配置。
